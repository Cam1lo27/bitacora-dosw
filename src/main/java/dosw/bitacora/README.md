# Semana 4: Análisis de Requerimientos
## ¿Qué entendía mal antes?

- Pensaba que el análisis de requerimientos era solo describir lo que el sistema debía hacer, sin tanto detalle.

- No entendía la importancia de estructurar correctamente un requerimiento con elementos como precondiciones, flujos y reglas de negocio.

- Creía que los diagramas, como el de contexto o los casos de uso, eran solo complementos visuales y no parte fundamental del análisis.

- No veía la diferencia entre una descripción general y un requerimiento realmente detallado.

## ¿Qué entiendo ahora?

- Entiendo que el análisis de requerimientos es la base del desarrollo de un sistema y define claramente qué se va a construir.

- Comprendo que un requerimiento bien estructurado debe incluir: nombre, descripción, actor principal, precondiciones, datos de entrada y salida, flujo básico, flujos alternos y reglas de negocio.

- Ahora veo que el diagrama de contexto ayuda a identificar los actores externos y su relación con el sistema.

- Entiendo que los diagramas de casos de uso permiten visualizar cómo interactúan los actores con el sistema.

- Comprendo que las reglas de negocio son fundamentales para definir restricciones y condiciones que el sistema debe cumplir.

## ¿Qué me falta reforzar?

- Practicar más la redacción clara y precisa de requerimientos funcionales.

- Mejorar la identificación de flujos alternos y posibles errores desde la etapa de análisis.

- Fortalecer la elaboración de diagramas de casos de uso correctamente estructurados.

- Aprender a definir reglas de negocio más completas y realistas según el contexto del sistema.
